### 왜 서버가 먼저인가
구 서버의 `TimelineSlotSchema.month`는 `required`였다.
신 FE가 보내는 `{ week, projects }`를 구 서버가 받으면 `month` 없다고 거절한다.
반대로 구 FE가 보내는 `month` 슬롯은 **신 서버가 조용히 버릴 뿐** 깨지지 않는다.
비대칭이므로 서버를 먼저 올리는 쪽이 안전하다.

### ⚠️ Actions success ≠ 라이브 반영
`Build & Deploy API`가 하는 일은 이미지 푸시 + `create-container-service-deployment` **호출**까지다.
Lightsail nano가 이미지를 받아 헬스체크(interval 10s × healthyThreshold 2)를 통과하기까지
**Actions 성공 후 약 3분**이 더 걸렸다. 그 사이 라이브 swagger는 여전히 `month`를 서빙했다.

→ Actions 초록불만 보고 FE를 밀었다면 그 3분 동안 신 FE ↔ 구 서버 조합이 된다.
**swagger가 `week`를 서빙할 때까지 폴링한 뒤** FE를 밀었다(17회 폴링, 10초 간격).

라이브 확인용 swagger 경로는 `/api-docs/swagger.json`이다 (`/api-docs.json`, `/swagger.json`은 404).

### 서버 변경 (`cce2853`)
- `TimelineSlotSchema`: `month(required)` 폐기 → `week: Number`(1-based 시작주차). `month`는 legacy optional로 잔존
- 시작주만 저장하고 **점유 구간은 저장하지 않는다** — 저장하면 프로젝트 기간 수정 시 둘이 어긋난다
- `_weekFromLegacyMonth`: `week` 없는 구 문서를 `startDate` 기준으로 환산해 read 시 내려줌
- `saveTimeline`: week 정수·1이상·프로젝트 존재 검증 통과분만 저장
- `CurriculumWeekSchema.description` 추가(주차당 설명 1건). `items`는 레거시 읽기 호환으로 유지

커밋 전에 `models/CareerPlan.js`·`routes/careerPlan.js`의 주석이 1차 구현 시절 문구
("startDate 부터 7일 블록")로 남아 있는 걸 발견해 정정했다. 실제 규칙은 **월~일 달력 주**다.

### 2. ⚠️ 로컬 빌드에 API base URL 이 없었다

"로컬 빌드 해시 ≠ 라이브 해시"를 검증법 문제로만 적었는데, 원인을 파보니 **진짜 버그**였다.

`apps/*/vite.config.ts` 에 **`envDir` 이 없어** Vite 가 각 앱 디렉터리에서만 env 를 찾았다.
`.env.production` 은 모노레포 **루트**에 있으므로 무시됐고, 로컬 빌드는
`VITE_API` 가 `undefined` 인 채로 만들어지고 있었다.

```
grep -o 'api.lighthouse.career' apps/app/dist/assets/index-*.js   # → 0건
```

CI 는 워크플로우가 `VITE_API` 를 직접 주입해서 통과할 뿐이었다. 해시 차이는 그 부산물.
`envDir` 을 루트로 잡으니(=`publicDir` 과 같은 패턴) 양쪽이 완전히 일치한다.

| | 로컬 | 라이브 |
|---|---|---|
| prod | `index-CCgTL8Du.js` | `index-CCgTL8Du.js` |
| test | `index-B4Dr35q3.js` | `index-B4Dr35q3.js` |

> 루트에 `.env.production` 이 **있는데도** 안 먹는 게 함정이다. 파일이 보이니 다들 읽힌다고 믿는다.
> pnpm workspaces + Vite 조합에서는 `envDir` 을 명시하지 않으면 앱 디렉터리 기준이다.

### 3. ⚠️ 운영 데이터 점검 — 배포 전제와 결과가 달랐다

`lighthouse-api/scripts/inspect-timeline-week-data.js` (읽기 전용) 로 고정했다.
`countDocuments` 와 projection 조회만 하고 쓰기·삭제·admin 명령은 하지 않는다.

배포는 "실사용 데이터 없음"을 전제로 마이그레이션을 생략했는데, 실측 결과:

```
career_plans      21건 / 타임라인 있음 15 / 레거시 month 슬롯 14 / 소유자 12명
weekly_schedules  18건 / weekStart 가 월요일 아님 7건   ← 구 주 경계
```

구 경계 7건은 2026-07-01 ~ 08-27 생성. **weekStart 를 월요일로 옮기는 것만으론 안 된다** —
구 주는 `weekStart..+6`(예: 수~화)이라 새 월~일 창 밖으로 나가는 항목이 레코드당 1~8건 생긴다.
제대로 하려면 항목을 주 단위로 재분배해야 한다. (유니크 인덱스 `(planId, weekStart)` 충돌은 0건)

→ 사용자 확인 결과 **전부 테스트 데이터**여서 고아 레코드로 남기고 넘어갔다.
해당 계정이 그 주 일정을 다시 열면 자동생성본이 보인다.

**교훈**: 데이터 유무를 눈대중으로 확정하지 말 것. 세는 걸 스크립트로 고정해두면
