## 🚨 함정 5종 (다시 밟지 말 것)

### 1. 인증 실패가 HTTP **200** 으로 온다
상태코드로 판정하면 에러 본문을 정상 데이터로 파싱한다.
→ **루트 태그를 검증**해야 한다(`client.js`).

### 2. `parseTagValue: false` 가 필수다
fast-xml-parser 기본값은 숫자로 변환한다. 직업코드 `020301` 이 `20301` 이 된다.
같은 이유로 **단일 항목은 배열이 아니라 객체**로 온다 → `asArray()` 헬퍼로 감쌌다.

### 3. 흥미 매칭이 **0건**이었다
API 는 `현실형(Realistic)` 로 주고 우리 마스터는 `현실형` 이다.
`normalizeName()` 에서 **괄호 안을 통째로 제거**해야 붙는다. 공백·`·`·`/` 도 함께 정규화.

### 4. `&#xd;` 가 화면에 그대로 보였다 (101건)
원본이 **이중 인코딩**이다. XML 파서가 한 겹 풀면 `&#xd;` 라는 **문자열**이 남는다.
→ `cleanText()` 로 한 겹 더 디코딩 (`d72543d`).
발견 경로가 중요하다 — DB 쿼리로는 안 보였고 **브라우저 스크린샷**에서 눈에 띄었다.

### 5. GitHub Actions cron 은 `L`(말일)을 모른다
`0 18 L * *` 로 썼더니 **422 Invalid cron** 이고, 그 상태에선 `workflow_dispatch` 도 막힌다.
워크플로 파싱 자체가 실패하기 때문이다. → `0 18 1 * *`(매월 2일 03:00 KST).

수치와 무관하게 남는 **구조적 논증**은 이것이다.

`calcTotalMatch` 의 모든 축이 `1 - |u - j|` 형태인데,
- `u` = 사용자의 **절대적 자기평가**(0~1)
- `j` = `weightedJobScore` 가 만든 **직업간 백분위**(0~100 → 0~1), 즉 **다른 직업 대비 상대값**

**단위가 다른 두 값을 빼고 있다.** 그래서 전 항목 백분위가 낮은 직업(예: 경비원)은

결과적으로 "당신에게 맞는 직업"이 아니라 **"전반적으로 평균에 가까운 직업"**을 고르게 된다.

직업 데이터 자체는 진짜다(공식 API). 경비원의 직업간 백분위가 전 항목 낮은 것은 사실이고,
그 사실과 위 계산 형태가 만나 생기는 문제다.

→ **재검증 방법을 바꿔야 한다.** 실사용자 응답이 아직 없으므로 응답 표본에 기대지 말고,

   따지는 편이 맞다. 이건 채점 함수와 직업 데이터만으로 판정되며 응답 표본이 필요 없다.
