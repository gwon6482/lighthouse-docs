### API: 부분 저장이 문서를 복제하던 문제 (`8fd4fa1`, 배포·라이브 확인)

설계는 "부분 응답도 저장"인데 제출 API 가 **호출마다 새 문서**를 만들었다. 파트마다 저장하면
한 사람이 문서 N개가 되어 **완주율은 낮게, 이탈은 많게** 부풀려진다.

→ 첫 응답의 `respondent_id` 를 다시 보내면 같은 문서를 갱신(200). 완주본은 409(정답지 재현 보호),
  설문지 다르면 409, 갱신 조건에 `completed:false` 재확인(경쟁 방어).
⚠️ 이어 쓰기의 시작 시각은 **처음 저장값**. 클라이언트 값을 믿으면 늦춰 보내는 것만으로 `too_fast` 를 피한다.

라이브 반영은 **새 코드만 내는 응답**으로 확인했다 — 잘못된 `respondent_id` 에 `"respondent_id 형식이 올바르지 않습니다"`
(옛 코드는 `role` 오류를 낸다).

### 랜딩 `/survey` (`97115b0`, **`dev` 에만 있음 — main 미반영**)

안내·동의 → 응답자 정보 → 성격 6장 → 재능 6장 → 흥미 → 가치관 → 업무 환경 → 완료.
`?c=<태그>` 로 수집 경로 구분.

지킨 것:
- 제출 경로는 **research** 쪽. 앱 경로로 보내면 사용자 "상위 N%" 가 오염된다
- 척도 값 'A'~'E'(A=매우 아니다) — 앱과 동일. 10-05 척도 뒤집힘 사고 재발 방지
- 직업은 검색 선택만(자유 입력 X) — 정답지라 jobCode 가 확정돼야 한다
- T1·T21 은 **화면 순서대로** 키를 넣는다(서버 직선응답 판정이 삽입 순서를 따른다)
- T3 는 고른 것만 보낸다 — 앱처럼 0 으로 채우면 서버가 'T3 까지 왔다' 고 오판한다
- 레이아웃 없음(매 로드 스플래시 제거), `noindex`
- 가치관 그림은 앱 도메인에서 lazy 로드, 업무 환경은 **설명문만**(그림 30장 48MB)

⚠️ 문항 수: **척도 104개(성격 43 + 재능 61) + 흥미 33 · 가치관 9 · 업무환경 6**.
   여기저기 적힌 "103문항" 은 **재능+흥미+가치관(61+33+9)** 의 합이다. 전체 문항 수가 아니다.
   (API 주석 `103문항을 3분 미만이면 의심` 도 같은 오해 — 판정 기준값엔 영향 없음)
