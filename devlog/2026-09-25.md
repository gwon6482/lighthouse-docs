## 9/23 의 전제가 불완전했다 — "검토 없이 즉시 게시"가 아니었다

9/23 일지는 "scope 가 비민감이라 구글 검토 없이 즉시 게시된다"고 적었다.
**검토(verification)가 불필요한 것은 맞다. 그런데 게시 자체가 브랜딩 필수항목을 먼저 요구한다.**

```
앱 게시 클릭 → "앱을 게시하려면 브랜딩 페이지에서 구성을 완료해야 합니다"
```

게시 최소 조합: 앱 이름 + 지원 이메일 + **홈페이지 URL** + **개인정보처리방침 URL**
+ 승인된 도메인 + 개발자 연락처. 서비스 약관은 선택.

우리에겐 **개인정보처리방침이 없었다.** 랜딩 `BACKLOG.md` 2번이 이미 "처리방침 링크는
사실상 필요하다"고 적어둔 구멍이 그대로 출시를 막았다.

> ⚠️ **로고를 업로드하지 말 것.** 외부 프로덕션 앱은 로고를 올리는 순간 brand-verification 이 붙는다.

  제8조에 사실대로 고지하고 주의 문구를 넣었다.

약관은 사업적 결정 3건을 반영했다: **만 14세 이상만 가입** / **게시물 저작권은 이용자

> ⚠️ 사업장 주소는 **넣지 않았다.** 처리방침의 법정 필수는 보호책임자 성명·연락처(법 제30조)이고,

## ⚠️ 리전을 지연시간으로 추론했다가 틀렸다

국외이전 조항을 쓰려고 Atlas 리전을 원격 확인했다. TCP 최소 RTT:

```
Atlas 샤드 35.1ms | AWS 서울 7.7ms | 도쿄 34.4ms | 홍콩 62.7ms | 싱가폴 74.9ms
```

도쿄와 거의 같아서 "일본"이라고 방침에 적었다. **콘솔 확인 결과 AWS Seoul(ap-northeast-2)** 이었다.

샤드 IP 대역 `159.143.0.0/16` 은 **MongoDB, Inc. 자체 소유(BYOIP)** 다. whois 는 뉴욕 본사만 나오고,
AWS `ip-ranges.json` 대조도 실패한다(AWS 대역이 아님). 서울 인스턴스라도 MongoDB 자기 네트워크를
경유해 우회 라우팅되면 그만큼 지연이 붙는다.

> **RTT 는 네트워크 경로를 재는 것이지 데이터가 저장된 위치가 아니다.**
> 법적 고지에 쓸 레지던시의 정본은 Atlas 콘솔의 Cloud Provider & Region 뿐이다.

## 랜딩 서브페이지가 **전부 403** 이었다

처리방침을 배포했는데 `/privacy` 가 403. 확인해보니 새로 만든 페이지만의 문제가 아니었다.

```
/ 200 | /our-story 403 | /reservation 403 | /mentor 403 | /business 403 | /privacy 403
/privacy/index.html 200   ← 파일은 정상 업로드돼 있었다
```

CF `EF4ZCNNTOKH1P` 오리진이 S3 **REST 엔드포인트**(OAC)인데 `DefaultRootObject: index.html` 은
**`/` 에만** 적용된다. `/privacy` 는 S3 키 `privacy` 를 찾고, 없으니 OAC 가 403 을 낸다
(404 가 아닌 이유는 존재여부 은폐).

홈에서 **클릭해 들어가면 SPA 라우팅**이라 잘 돈다. 깨지는 건 직접 URL·새로고침·외부 링크뿐이라
여태 안 드러났다. 그리고 **구글이 처리방침 URL 을 가져가는 방식이 정확히 그것**이다.

조치: CloudFront Function `lighthouse-landing-index-rewrite`(viewer-request).
끝이 `/` 면 `index.html`, 마지막 세그먼트에 점이 없으면 `/index.html` 을 붙인다.
점 있는 경로(`/_nuxt/*.js`, `/favicon.ico`, `/*_payload.json`)는 통과시킨다.

> ⚠️ **ES5 문법만 쓸 것**(`endsWith` 금지). publish 전에 `aws cloudfront test-function` 으로
> 경로별 검증할 것 — 9개 경로를 먼저 돌려보고 붙였다.
> apex `lighthouse.career` 는 www 로 301 만 하므로 함수 불필요.


## 탈퇴가 파기가 아니었다 — 하드 삭제로 전환

처리방침을 쓰다 발견했다. `DELETE /api/user` 가 `isActive=false` 만 찍고 문서를 그대로 뒀다.
이메일·이름·나이·성별·진로답변·검사결과가 전부 남는다. 그런데 방침은 "지체 없이 파기"라고
**이미 배포돼 있었다.** 문구만 고쳐선 안 된다 — 법 제21조상 탈퇴는 처리목적 달성이라 파기 의무가 생긴다.

삭제 범위는 모델 15개를 전수 확인해서 정했다.

| 대상 | 처리 | 키 |
|---|---|---|
| `users` | 삭제 | `uid` |
| `career_plans`/`weekly_schedules`/`achievement_records`/`curriculum_completions` | 삭제 | `userUid` |
| `survey_results` | 삭제 | `survey_id ∈ User.surveyResults` **OR** `respondent_id == uid` |
| S3 `lighthouse-uploads` | 삭제 | 접두사 `uploads/achievements/<uid>/` |
| `job_reviews` | **익명화**(submitterEmail 만 비움) | `submitterEmail == user.email` |
| `public_career_plans` | **제외** | 유저 참조 없는 큐레이션 콘텐츠 |

- `respondent_id` 는 클라이언트가 보내는 값이라 빌 수 있다 → OR 로 걸어야 안 놓친다
- S3 는 **접두사 기준**. photoUrl 을 훑으면 presigned 업로드만 되고 기록이 안 남은 고아 파일을 놓친다
- 후기는 본문이 공개 정보라 지우지 않고 식별자만 제거한다

> ⚠️ **삭제 순서는 딸린 것 먼저, `users` 문서 맨 마지막.** 중간 실패 시 계정이 남아 같은 토큰으로
> 재시도할 수 있다. 반대로 하면 재인증이 불가능해져 고아 데이터만 남는다.
> 트랜잭션은 쓰지 않았다 — S3 가 못 들어가고 DB 3개에 걸쳐 있어 얻는 것보다 복잡도가 크다.
