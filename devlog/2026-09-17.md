### 이메일 가입 vs 카카오 가입 — 무엇이 어디에 저장되나

둘 다 `user_data.users` 의 같은 `User` 문서다. 갈리는 것은 **누가 채우느냐와 계정이 언제 생기느냐**다.

| User 필드 | 이메일 (`register` 1회) | 카카오 (콜백 + `complete-profile`) |
|---|---|---|
| `email` | 입력값 | 동의 시에만. 미동의면 **없음**(sparse unique) |
| `passwordHash` | bcrypt(10) | **없음** → 이메일 로그인 영구 불가 |
| `authProviders` | `[{local, providerId: 이메일}]` | `[{kakao, providerId: 회원번호}]` |
| `name` | 위저드 입력 | 콜백이 닉네임으로 선채움 → 위저드에서 수정 |
| `age`·`gender` | 위저드 입력 | 콜백엔 없음 → `complete-profile` 에서만 |
| `onboarding` | `register` 본문에 동봉 | `complete-profile` 에서만 |
| 계정 생성 시점 | 위저드 **끝** | 위저드 **전**(콜백) |

마지막 줄이 구조적 차이의 뿌리다. 카카오는 계정이 먼저 생기므로 위저드 도중 이탈하면
**나이·성별·Q1~Q3 가 빈 계정이 DB 에 남는다.**

## 카카오만 lastLoginAt 이 안 찍히고 있었다

위 비교표를 만들다 발견했다. `login` 은 `lastLoginAt` 을 갱신하는데 `kakaoCallback` 은
기존 유저를 그대로 return 해서 **카카오 유저만 마지막 접속 집계에서 통째로 빠진다.**

### ⚠️ 여기서 `save()` 를 쓰면 로그인이 죽을 수 있다

`login` 이 `user.save()` 를 쓰니 따라 쓰고 싶어지지만, `save()` 는 **문서 전체 검증을 다시 돌린다.**
옛 계정에 스키마와 어긋난 값이 하나라도 있으면 그 사용자는 **로그인 자체가 실패한다.**
필드 하나 찍자고 낼 대가가 아니다 → `updateOne({$set:{lastLoginAt}})`.

```js
const now = new Date();
await User.updateOne({ _id: existing._id }, { $set: { lastLoginAt: now } });
existing.lastLoginAt = now;   // 호출부가 방금 쓴 값을 보게
```

신규 가입 경로(`User.create`)에도 `lastLoginAt` 을 넣어 두 경로를 맞췄다.

카카오로 가입을 마친 직후 브라우저 뒤로가기를 누르자 '로그아웃하시겠어요?' 가 뜨고 실제로
로그아웃됐다. 다시 로그인하니 위저드를 건너뛰고 메인으로 갔다 — **뒤는 정상이다.**
답변이 이미 저장돼 있으니(`answeredAt`) 다시 물을 이유가 없다. 문제는 앞쪽 하나뿐이었다.

### 전제가 조용히 깨져 있었다

R5(인증 경계)는 2026-07-22 에 세웠다. "토큰을 쥔 채 로그인 화면에 닿음 = 로그아웃 의도".
당시엔 그 자리에 닿는 길이 의도적 뒤로가기뿐이라 맞는 전제였다. 소셜 로그인이 이걸 깼다.

가입을 마치고 뒤로가기 한 번이면 곧장 로그인 화면이고, 가드는 그걸 '로그아웃 의도'로 읽었다.

## 구글 로그인 배선 — 키만 넣으면 켜지는 데까지

카카오와 같은 fail-closed 구조로 넣었다. `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`/
`GOOGLE_REDIRECT_URI` 셋이 다 있을 때만 켜지고, 없으면 `providers` 가 `google:false` 를
보고하고 `/api/auth/google` 은 503 이다. **이 배포만으로는 사용자에게 아무 변화가 없다.**

### 제공자별로 계정 정책을 두지 않았다

카카오 코드를 복사해 구글용으로 고치는 게 가장 빠른 길이었지만 그러지 않았다.
신원 판단·이메일 충돌·`lastLoginAt` 규칙이 **반드시 갈라지기** 때문이다.

```
findOrCreateSocialUser({provider, providerId, email, name})   ← 정책은 여기 하나
  ↑ normalizeKakaoProfile / normalizeGoogleProfile            ← 응답 모양만 맞춘다
signState() / issueAppToken()                                  ← state·JWT 도 공통
```

카카오도 이 공통 함수를 쓰도록 바꿨다(회귀 없음을 로컬에서 확인).

### 구글에서 다른 점만

| | 카카오 | 구글 |
|---|---|---|
| 신원 | 회원번호 | `sub` |
| scope | 콘솔 동의항목(생략 가능) | **필수** `openid email profile` |
| 이메일 | `is_email_valid && is_email_verified` | `email_verified` |

> ⚠️ `prompt=select_account` 를 붙였다. 없으면 브라우저에 구글 세션이 하나 있을 때
> **묻지도 않고** 그 계정으로 들어가서 다른 계정으로 바꿀 방법이 없다.

> ⚠️ `email_verified:false` 인 이메일은 저장하지 않는다. 받으면 그 이메일의 주인이 아닌
> 계정이 우리 쪽 이메일 칸을 차지할 수 있다.

### 더미 키로 여기까지 검증했다

실제 구글 클라이언트 없이도 확인되는 것이 많다. 로컬에 더미 키를 넣고 띄웠다.

```
authorize 리다이렉트 → accounts.google.com/o/oauth2/v2/auth
  scope=openid email profile / prompt=select_account / redirect_uri 일치
  state 안의 복귀지 = app 도메인, client_secret 미노출
?redirect=https://evil.example → 허용목록 밖이라 무시하고 기본 복귀지로
콜백 state 위조 → ?error=invalid_state / 사용자 취소 → ?error=cancelled
```

정규화·플래그·라우트 단위 확인 17건도 함께 통과. **남은 것은 실제 키와 콘솔 등록뿐이다.**

### 사람이 해야 하는 일 (구글 클라우드 콘솔)

1. Google Cloud Console → 프로젝트 → **API 및 서비스 → OAuth 동의 화면** 구성(외부/앱 이름/지원 이메일)
2. **사용자 인증 정보 → OAuth 클라이언트 ID → 웹 애플리케이션**
3. **승인된 리디렉션 URI** 에 정확히 이 값 하나:
   `https://api.lighthouse.career/api/auth/google/callback`
   ⚠️ 한 글자라도 다르면 `redirect_uri_mismatch`. 끝의 `/` 하나까지 같아야 한다.
4. 발급된 클라이언트 ID/시크릿을 레포 시크릿에 등록:
   ```
   gh secret set GOOGLE_CLIENT_ID     --repo gwon6482/lighthouse-api   # 값은 프롬프트/stdin
   gh secret set GOOGLE_CLIENT_SECRET --repo gwon6482/lighthouse-api
   gh secret list --repo gwon6482/lighthouse-api                       # 반드시 확인
   ```
   ⚠️ `gh secret set NAME value` 는 **안 된다**(인자 1개만 받는다). 그리고 `--repo` 없이 쓰면
   **현재 폴더의 레포**에 들어간다 — 2026-09-10 에 두 번 다 당했다.
5. 아무 커밋이나 `main` 에 push(= 재배포). 시크릿만 넣으면 서버에 안 들어간다.
6. 확인: `curl https://api.lighthouse.career/api/auth/providers` → `google:true`

FE 는 이미 `providers` 를 읽어 버튼을 켜므로 **재배포 없이** 살아난다.

### ⚠️ 재배포용 '빈 커밋'은 워크플로를 트리거하지 않는다

구글 시크릿을 등록하고 `providers` 를 보니 그대로 `google:false` 였다. 원인은 예상대로
**재배포를 안 해서**였는데(시크릿 등록만으로는 컨테이너에 안 들어간다), 재배포하려고 만든
`git commit --allow-empty` 가 **아무 워크플로도 돌리지 않았다.**

`deploy.yml` 에 `paths-ignore`(`**.md`, `docs/**`)가 걸려 있다. 변경 파일이 **하나도 없는**
커밋은 경로 필터를 통과하지 못해 푸시해도 Actions 가 뜨지 않는다. push 는 성공하고
`git log` 에도 남으니 **조용히 아무 일도 안 일어난다** — 가장 알아채기 어려운 실패다.

```
git push      → 8d91ddc..f4ce35a  main -> main    (성공처럼 보인다)
gh run list   → 새 run 없음                        (실제로는 아무 일도 없었다)
```

해결: `workflow_dispatch` 가 열려 있으니 수동 트리거가 가장 깔끔하다.

```bash
gh workflow run "Build & Deploy API" --repo gwon6482/lighthouse-api --ref main
gh run list --limit 1     # event 가 workflow_dispatch 인지 확인
```

> 💡 **env 만 바꿔 재배포할 때는 빈 커밋 대신 `workflow run` 을 쓸 것.**
> 빈 커밋을 쓰려면 `paths-ignore` 를 빼야 하는데, 그건 문서 수정마다 배포가 도는 대가를 치른다.

### 구글 켜짐 — 라이브 확인

```
GET /api/auth/providers → {"kakao":true,"google":true,"apple":false}
GET /api/auth/google    → 302 accounts.google.com/o/oauth2/v2/auth
   client_id 728773260334-… / redirect_uri 일치 / scope=openid email profile
   prompt=select_account / state 복귀지 = test 도메인 / client_secret 미노출
리다이렉트를 따라가면 **구글 로그인 화면(200)** 까지 도달
```

> 💡 로그인 화면까지 갔다는 건 **client_id 와 리디렉션 URI 가 콘솔 등록값과 일치**한다는 뜻이다.
> 하나라도 틀리면 로그인 화면 대신 `redirect_uri_mismatch` 400 이 온다(카카오 KOE006 과 같은 성격).

FE 는 **재배포 없이** 버튼이 살아났다 — `providers` 응답만 보고 켜지기 때문이다.
스테이징 로그인 화면에 '카카오로 로그인'·'구글로 로그인' 두 개가 나란히 뜨는 것을 실측했다.

**남은 것**: 실제 구글 계정 왕복(사람). 동의 화면이 '테스트 중'이면 **테스트 사용자에 등록된
계정만** 로그인된다(그 외에는 `access_denied`). 왕복이 끝나면 프로덕션 태그.
