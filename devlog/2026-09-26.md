## 요청은 test 셸이었지만 거기엔 둘 수 없었다

사용자 요청: "test.lighthouse.career 에서의 서비스 전체 계정관리".

`test` 셸은 **S3+CloudFront 정적 SPA라 서버가 없다.** 계정 목록·삭제를 하려면 브라우저가
`ADMIN_API_KEY` 를 들고 있어야 하는데, 정적 번들에 넣으면 누구나 JS 에서 꺼낼 수 있다.
그러면 계정 삭제뿐 아니라 `/api/admin/*` 전체(문항·후기·통계)가 통째로 열린다.

실측으로 확인한 조건:
- `test.lighthouse.career` → 200, **인증 게이트 없음**
- test 셸이 보는 API = `api.lighthouse.career` — **app 과 같은 프로덕션 DB**
- 어제 탈퇴를 하드 삭제로 바꿔서 **되돌릴 수 없다**

어드민은 `src/app/api/proxy/[...path]/route.ts` 가 NextAuth 세션을 검증한 뒤 **서버에서**
`x-admin-key` 를 주입한다. 정적 SPA 에는 그 자리가 없다. → 어드민으로 확정.

> 💡 `packages/core` 의 `MyPage` 는 계정관리가 아니라 콘텐츠 허브다. 그리고 test·app **공용**이라
> "test 에만 있는 화면" 같은 건 애초에 없다. `apps/test`·`apps/app` 은 각각 `main.ts` 한 파일뿐이다.

## 삭제 로직을 services 로 빼냈다

어제 `deleteAccount` 에 인라인으로 넣은 것을 `services/userPurge.js` 로 옮기고,
관리자 삭제가 **같은 함수**를 부르게 했다. 따로 두면 삭제 대상 컬렉션이 추가됐을 때
한쪽만 고쳐져 고아 데이터가 남는다.

## 신규 API

| 엔드포인트 | 내용 |
|---|---|
| `GET /api/admin/users` | 목록. page/limit(≤100)/search/provider/isActive + 딸린 데이터 건수 |
| `GET /api/admin/users/:uid` | 상세. 가입설문·자기이해검사·진로탐색·진로설계 |
| `POST /api/admin/users/:uid/reset` | 단계별 리셋 |
| `DELETE /api/admin/users/:uid` | 영구 삭제 |

⚠️ 목록의 건수 집계는 **컬렉션당 aggregate 1회(총 4회)**. 유저마다 `countDocuments` 를 돌리면 N+1 이다.
⚠️ `search` 는 정규식 메타문자를 이스케이프한다. 입력을 그대로 넣으면 `(` 하나로 터지고 ReDoS 도 가능.
⚠️ 진로계획은 **요약만** 싣는다(projects/timeline 원문 제외). 안 그러면 응답이 비대해진다.

## 🚨 단계별 리셋 — 이메일 계정에선 위저드가 안 뜬다

누적 3단계: `design`(설계·달성) → `survey`(검사·추천·북마크·목표진로) → `signup`(이름·나이·성별·가입설문).

테스트용이다. 같은 소셜 계정으로는 재가입이 불가능해서(providerId 가 같으면 같은 계정)
가입 플로우를 다시 밟으려면 계정을 지우거나 리셋이 필요하다.

그런데 앱 진입 가드가 이렇다:

```js
const socialOnly = providers.some(p => p.provider !== 'local')
              && !providers.some(p => p.provider === 'local')
if (socialOnly && !auth.user?.onboarding?.answeredAt) → 위저드로
```

**소셜 계정만 검사한다.** 이메일 계정은 `onboarding` 을 지워도 `/main/before` 로 간다.

가드를 "local 이 없으면 소셜"로 뒤집으면 주석이 경고하는 대로 **authProviders 가 빈 옛 계정이
위저드에 갇힌다**(2026-09-09 이전 이메일 가입자가 실제로 해당). 그래서 가드는 건드리지 않고:
- 리셋 응답에 `wizardWillShow` 를 실어 보내고
- 이메일 계정 모달에 경고 배너를 띄운다

⚠️ 유저 문서 갱신은 `save()` 가 아니라 `updateOne`. `save()` 는 문서 전체 검증을 다시 돌려서
옛 계정에 스키마와 어긋난 값이 하나라도 있으면 **리셋 자체가 실패한다**(lastLoginAt 때와 같은 함정).

## 어드민 로그인이 "로그인 중..." 에서 멈춘 건 — 재현 못 했다

사용자가 Vercel 에서 계정 env 를 바꾼 뒤 무한 로딩을 겪었다. 조사했지만 재현하지 못했다.

| 검증 | 결과 |
|---|---|
| 프로덕션 `csrf`·`providers`·`session` | 전부 200 |
| 자격증명 콜백(틀린 비번) | 302 + `?error=CredentialsSignin`, JSON 정상 |
| 손상된 세션 쿠키 | 정상 처리(`/dashboard` → 307 `/login`) |
| 로컬 브라우저 틀린 비번 / 맞는 비번 | 에러 표시 ✅ / `/dashboard` 도달 ✅ |

대신 **진단을 막던 구조**를 고쳤다.

```ts
const result = await signIn(...);   // reject 하면
if (result?.error) ...              // 여기 못 옴
setLoading(false);                  // 여기도 못 옴 → 영원히 "로그인 중..."
```

try/catch 가 없어 화면에 단서가 0개였다. next-auth v5 beta 의 `signIn` 은 응답 모양에 따라
throw 한다(`new URL(data.url)` 에서 `data.url` 이 비면 TypeError).

함께 `router.push` → `window.location.assign`. App Router 는 RSC 를 캐시하는데
**로그인 전에 받아둔 `/dashboard` 페이로드**는 세션이 없던 시점의 것이라,
layout 의 `auth()` 가 null 을 보고 `/login` 으로 되돌린다.

> ⚠️ 이 커밋은 원인을 특정한 게 아니라 **다음에 원인이 화면에 뜨게** 만든 것이다.

### 배제한 가설 (근거 있음 — 다시 뒤지지 말 것)
- `AUTH_SECRET` 미설정 → csrf·session 200
- 옛 세션 쿠키 복호화 실패 → 손상 쿠키로도 정상
- `_getSession` 미할당(SessionProvider 없음) → 기본값이 no-op 함수라 await 통과
- 클라이언트가 잘못된 origin 호출 → `apiBaseUrl` 은 클라이언트에서 **상대경로** 반환

## 브라우저 검증 중 잡은 버그

상세에서 이메일 가입 계정에 "비밀번호 없음 — 소셜 전용" 이 떴다.
`User.findOne({uid}, { passwordHash: 0 })` 로 **projection 에서 빼놓고** `!!user.passwordHash` 로
판정해 **항상 false** 였다. 읽어 와서 유무만 판정하도록 고쳤다(값은 응답에 안 싣는다).
